## Phases

| Phase | Status | Notes and limitations |
|---|---|---|
| Repository assessment | Done | [assessment.md](assessment.md), [capabilities.md](capabilities.md). |
| A — Instrumentation foundation | Done | Sessions (start/pause/resume/stop/clear/dispose), collector lifecycle and health, profiles, sampling, filtering, redaction, retention, backpressure, versioned schema. |
| B — Component and render profiler | Done, within framework limits | Per-component render timing requires `ProfiledComponentBase`; framework metrics give per-type parameter updates only. Render-batch timing boundaries are documented per hosting model. The component tree renders lazily and caps 500 children per level. An end-to-end test measures the dashboard with about 19,000 instances and 58,000 events (see [overhead](overhead.md#dashboard-at-scale)). |
| C — Unnecessary rendering diagnostics | Done | BP1001–BP1008. Identical-output detection needs `TrackRenderOutput`; BP1008 (components recreated) needs disposal events from `ProfiledComponentBase`. |
| D — Event handler profiler | Done | Handler duration, synchronous portion (instrumented receiver), correlated batches/HTTP/interop, rapid streams, duplicate requests. Time "awaiting external operations" is reported as overlap with HTTP requests started by the handler, not as measured wait time. |
| E — HTTP and network | Done for `IHttpClientFactory` and handler-wrapped clients | Passive observation of every `HttpClient` through `System.Net.Http` diagnostics was not implemented: the runtime redacts query values in its activity tags, which would make duplicate detection unreliable. Cache indicators are available in WebAssembly only (Resource Timing). |
| F — JavaScript interop | Done (WebAssembly); opt-in (Server) | The server cannot decorate `IJSRuntime` (the framework casts it to an internal type), so server profiling uses `IProfiledJSRuntime`. JS-to-.NET calls are recorded by the browser module in both hosting models (method name, instance or static, duration until .NET returned, estimated size), without the .NET type of the target object, which JavaScript does not know. On Blazor Server the arguments of .NET-to-JavaScript calls through `IProfiledJSRuntime` are measured from the circuit messages (including `byte[]` arguments, which the framework sends in messages of their own). Bytes passed through stream references are recorded in both directions (`DotNetStreamReference` arguments over seekable streams, `IJSStreamReference` results, JavaScript stream references passed to .NET); streams that cannot seek have no size. |
| G — Runtime, memory, allocations | Done | Public runtime APIs only. WebAssembly builds with `EnableDiagnostics` get CPU, GC dump, and counter captures from the toolbar (`.nettrace` downloads); on the server use `dotnet-trace`/PerfView alongside. Retained components (BP5004) are detected through weak references; likely retainers (event subscriptions on referenced services, static events, `DotNetObjectReference`, timers) are found heuristically, other retaining paths need a heap dump. Render allocations of instrumented components are measured per render (BP5005); other allocations are process-wide and attributed by time. |
| H — Blazor Server and circuits | Done | Lifecycle, connection state, inbound activities with hub method names, per-circuit correlation and isolation, round-trip batch timing. Reconnection is covered end to end (connection down and up, collection resumes on the same circuit). Message sizes are measured by wrapping Blazor's SignalR hub protocol: bytes per render batch, per received message, and per .NET-to-JavaScript call (BP6006). Not available: per-circuit memory (the runtime exposes process-wide memory only). |
| I — Unified timeline and causal analysis | Done | Lanes with overlap rows, zoom, pan, search, range selection, event details with operation-related events, causal (same-operation) highlighting, bookmarks, dropped-event markers. Comparison between sessions and between two windows of one session. |
| J — Diagnostic engine | Done | 53 rules with ids, versions, severity, confidence, evidence quality, impact method, caveats, suppression, threshold and per-rule overrides, extensibility. Optional AI explanations of findings through `IFindingExplainer` (an `IChatClient` adapter on the server; off by default). |
| K — Dashboard | Done | All sections. Keyboard support for lists, tables, tree, timeline, and drawer; respects light/dark and reduced motion. Every view, an open finding, the event drawer, and the in-page toolbar are audited with axe-core against WCAG 2.1 A and AA in light and dark color schemes by an end-to-end test (names, roles, grid structure, contrast). An automated audit does not replace testing with a screen reader, which has not been done. |

## Deviations from the plan

- **Dashboard technology.** The dashboard is plain JavaScript served as static assets instead of a Blazor component, so that
  viewing profiling data never perturbs the measured app (no extra render batches, circuit traffic, or interop).
- **Server JS interop** is opt-in, as explained above.
- **Passive HTTP observation** was replaced by the handler-based collector, as explained above.

| Second competitive study | Done | [competitive-analysis.md](competitive-analysis.md#second-study-late-november-2026). MCP endpoint and CLI MCP server, Long Animation Frame script attribution and BP7006, frustration signals and BP7007, BP5004 retainers, BP1008, OpenTelemetry, Responsiveness view, render-tree flame graph, per-component comparison, allocation regression gate for benchmarks. End-to-end tests cover rage and dead clicks, component recreation, forced layout attribution in WebAssembly, the MCP endpoint, the Responsiveness view, and the flame graph. Retainer detection is heuristic (references held by the component's own fields and static events); other retaining paths still need a heap dump. |

## Known gaps to address next

None from the competitive studies. WebMCP itself is still an origin trial in Chrome; the in-page agent tools follow its
draft API (`document.modelContext.registerTool` with an abort signal) and are verified against Chromium's implementation.
